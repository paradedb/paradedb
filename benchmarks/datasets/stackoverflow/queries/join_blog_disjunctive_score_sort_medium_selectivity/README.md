# Blog Query 2 (Medium Selectivity): Universal Disjunctive Search Across 3-Table Hierarchy (Score Sort)

- **Join**: `users` → `stackoverflow_posts` → `comments`
- **Description**: Disjunctive (`OR`) search for `'python'` across all three normalized tables (`users.about_me ||| 'python' OR stackoverflow_posts.title ||| 'python' OR comments.text ||| 'python'`), ranked by composite relevance score (`pdb.score(users.id) + pdb.score(stackoverflow_posts.id) + pdb.score(comments.id)`), projecting real display columns (`users.display_name`, `stackoverflow_posts.title`, `comments.score`).
- **Highlights**:
  - Relational equivalent of an "all-fields" search on a denormalized Elasticsearch document.
  - Exercises single-pass predicate tagging, lazy `ctid` resolution (`VisibilityFilterExec`), and deferred string decoding (`TantivyDecodeExec`).

## Query Info (statistics from 20m dataset):

- `'python'` selectivity:
  - `comments.text ||| 'python'`: ~221K matches (~0.76%, ~216K joined rows)
  - `stackoverflow_posts.title ||| 'python'`: ~170K matches (~0.85%, fanning out to ~333K joined rows)
  - `users.about_me ||| 'python'`: ~24K matches (~1.07%, fanning out to ~1.05M joined rows)
  - Combined disjunctive (`OR`) joined selectivity: ~5.27% (~1.50M / 28.45M joined rows).

## Native PostgreSQL Variants

- **`postgres.sql` (~119.0 s)**:
  - The natural, un-rewritten PostgreSQL query with a cross-table `OR` filter (`u.about_me @@ q OR p.title @@ q OR c.text @@ q`).
  - Because the disjunction spans three tables, PostgreSQL cannot use per-table GIN indexes and executes a full 3-table `Parallel Seq Scan` + `Parallel Hash Join` across all 28.45M joined rows, while also suffering from `NULL` score propagation when `users.about_me` (81.5% `NULL`) or `stackoverflow_posts.title` (61.5% `NULL`) is `NULL`.
  - Retained only in this medium-selectivity tier to demonstrate the natural baseline without adding 40 minutes to CI across all three selectivity tiers.
- **`postgres_union_agg.sql` (100% exact recall)**:
  - Rewrites the cross-table `OR` into a 3-branch `UNION ALL` where each branch drives from one table's GIN index, computes `ts_rank()` inside an optimization-fenced subquery (`WITH _ AS (SELECT 1)`, preventing `pull_up_subqueries` from flattening the branch so PostgreSQL can use `Parallel Append` and avoid redundant `to_tsvector()` evaluations across the `1:N` join fanout), and joins the other two tables (`enable_indexonlyscan = off` prevents ParadeDB's BM25 index-only scan cost estimate from hijacking unpredicated B-Tree join legs).
  - Because a qualifying `(user, post, comment)` triple can match in any non-empty subset of the 3 tables (`2^3 - 1 = 7` possible `(u_match, p_match, c_match)` bitmasks) and each branch only knows one table's partial score (`u_score`, `p_score`, or `c_score`), no branch knows a row's final composite score `u_score + p_score + c_score` until all three branches are expanded across the joins and combined via `GROUP BY u_id, display_name, p_id, title, c_id, comment_score` (`SUM(part_score)`).
  - **Tradeoff**: Guarantees 100% exact recall across all match combinations, but cannot push `ORDER BY ... LIMIT` into any branch: at medium selectivity it must expand the `1:N` join fanout (23K matching users fanning out to ~1.05M comments, with the planner switching several join legs from B-Tree `Nested Loop` to `Parallel Hash Join` + `Parallel Seq Scan` over `stackoverflow_posts`, `comments`, and `users`) and hash-aggregate ~1.53M rows before sorting.
- **`postgres_early_topk.sql` (20/20 recall on this dataset, up to 1 `float4` ULP tie-break order)**:
  - Exploits `ts_rank() >= 0` and the `1 : N : M` foreign-key hierarchy (`users → stackoverflow_posts → comments`, where going down is a `1:N` fanout and going up is an `N:1` lookup) to push `ORDER BY ... LIMIT` _below_ the B-Tree joins in each branch.
  - Instead of grouping by which single table matched, it partitions the 7 `(u_match, p_match, c_match)` bitmasks by the **deepest (most specific) table in the hierarchy that matched**, and pre-joins any _ancestor_ matches in memory so each branch has its complete cumulative score before expanding child B-Tree joins:
    1. **Branch 1 — Deepest match is `users` (`(1, 0, 0)`)**: When only `users.about_me` matches (`p_score = 0, c_score = 0`), every post and comment owned by user `u` shares the exact same score `u_score`. Branch 1 sorts the GIN-matching `users` by `u_score DESC LIMIT 100` _first_ and lazily expands `stackoverflow_posts → comments` via `CROSS JOIN LATERAL` + `Incremental Sort (u_score DESC, c_id DESC) LIMIT 20`, halting as soon as the top 2 users produce 20 comments (avoiding the 1.05M-row `1:N` fanout across all 23K matching users).
    2. **Branch 2 — Deepest match is `stackoverflow_posts` (`(0, 1, 0)` and `(1, 1, 0)`)**: When `comments.text` does not match (`c_score = 0`), the score `up_score = COALESCE(u_m.u_score, 0) + p_score` is fully determined at the `stackoverflow_posts` level. Branch 2 computes `up_score` via an in-memory `Parallel Hash Left Join` between GIN-matching `stackoverflow_posts` and GIN-matching `users` (`u_m`), sorts the posts by `up_score DESC LIMIT 100` before touching `comments`, and lazily expands `comments` (`comments_post_id_idx`) and `users.display_name` (`users_pkey`) via `CROSS JOIN LATERAL` + `Incremental Sort (up_score DESC, c_id DESC) LIMIT 20` (halting after inspecting ~16 posts).
    3. **Branch 3 — Deepest match is `comments` (`(0, 0, 1)`, `(0, 1, 1)`, `(1, 1, 1)`)**: Rather than probing `stackoverflow_posts_pkey` and `users_pkey` ~228K times before sorting, Branch 3 builds an in-memory hash table `p_m` of only the GIN-matching posts left-joined with GIN-matching users (carrying `up_score`) and `Parallel Hash Left Join`s the GIN-matching `comments` against `p_m` on `c.post_id = p_m.id` to compute `upc_score = COALESCE(p_m.up_score, 0) + c_score`. It sorts the comments by `upc_score DESC, c.id DESC LIMIT 100`, takes the top 20, and probes `stackoverflow_posts_pkey` and `users_pkey` via `CROSS JOIN LATERAL` only 20 times at the end to hydrate `u_id`, `display_name`, and `title`.
    4. **Inner `LIMIT 100` per parallel subquery**: Without an inner `LIMIT`, parallel workers under `Gather Merge` sort all matching rows and fill their 64 KB `shm_mq` tuple queues when the outer `Incremental Sort + Limit 20` stops early, blocking worker exit and starving subsequent `Append` branches of parallel workers (`max_parallel_workers = 8`).
    5. **Outer `GROUP BY ... MAX(score)`**: Because each branch already accumulates ancestor scores along its hierarchy path (`u_score`, `u_score + p_score`, and `u_score + p_score + c_score`), a multi-table match that also appears in an ancestor branch's top 20 already carries its complete score in the deepest matching branch; the outer query therefore deduplicates the `<= 60` candidates with `MAX(score)` rather than `SUM(score)`.
  - **Tradeoff**: Avoids `1:N` join fanout and ~228K random B-Tree probes, but relies on two structural assumptions that could affect recall on adversarial data:
    1. **The `(1, 0, 1)` hierarchy-gap approximation**: A `comments` row stores `post_id`, not `owner_user_id` (`comments.user_id` is the comment author, whereas the query joins on `stackoverflow_posts.owner_user_id = users.id`). Because Branch 3's hash table `p_m` only includes posts whose `title` matched the GIN query, if `users.about_me` and `comments.text` both match (`1`) but the intermediate bridge row `stackoverflow_posts.title` does _not_ match (`0`), `c.post_id` misses in `p_m`. Branch 3 cannot link the comment to its grandparent user `u_m` without probing `stackoverflow_posts_pkey` for every matching comment, so a `(1, 0, 1)` triple is scored as `u_score` in Branch 1 and `c_score` in Branch 3 (`MAX(score) = max(u_score, c_score)` instead of `u_score + c_score`).
    2. **The `LIMIT 100` parent lookahead window**: Sorting parent rows (`users` in Branch 1, `stackoverflow_posts` in Branch 2) before expanding child `comments` assumes the top 100 parent rows join to at least 20 child `comments` (since an `INNER JOIN` drops parent rows with 0 comments).
       On this dataset, 3,356 three-way `(1, 1, 1)` matches exist whose 3-table scores strictly dominate 2-table matches. (At the 20th-place tie boundary `score = 0.21952924`, 2 tied `(1, 1, 1)` rows differ from `postgres_union_agg.sql` by 1 `float4` ULP (`1e-8`) because `postgres_early_topk.sql` sums `(u_score + p_score) + c_score` in fixed hierarchy order whereas `postgres_union_agg.sql` evaluates `SUM(part_score)` (`real`) across a `Parallel Append` in non-deterministic worker arrival order.)
