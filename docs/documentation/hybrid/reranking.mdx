Retrieval is a funnel. [Fusion](/documentation/hybrid/rrf) narrows millions of rows to a few hundred candidates using signals that are cheap to compute over the whole index. Reranking then reorders those few hundred using signals that would be too expensive to apply to everything.

Reranking **reorders**; it does not filter. Every candidate receives a new score, the list is re-sorted, and the final `LIMIT` truncates it. A weak result leaves the top 10 only because a better one took its place, which means reranking can relocate quality but never create it. If the right row is not in the candidate set, no reranker recovers it.

## Fetch Enough Candidates

Because reranking is bounded by what fusion returned, the branch `LIMIT` matters more than any reranking parameter. Fetch 100 to 200 candidates per branch for a top-10 result, and confirm both branches still push down with `EXPLAIN`.

Measure the two stages separately. Fusion is judged on whether the relevant rows made it into the candidate set at all; reranking is judged on the order of the rows you actually display. A drop in quality comes from one or the other, and the fixes are unrelated.

## Reranking on Columns

The most common reranking signals are already columns in your table. Because the candidate set is a CTE, reranking is an expression over a join.

This example decays the fused score by age and penalizes out-of-stock rows:

<CodeGroup>
```sql SQL
WITH lexical AS (...), semantic AS (...), fused AS (...)
SELECT m.id, m.description,
       f.score
         * (1 + 0.3 * exp(-extract(epoch FROM now() - m.created_at) / (30 * 86400)))
         * CASE WHEN m.in_stock THEN 1.0 ELSE 0.4 END
       AS final_score
FROM fused f
JOIN mock_items m USING (id)
ORDER BY final_score DESC, m.id
LIMIT 5;
```

</CodeGroup>

The recency term is an exponential decay with a 30-day time constant, scaled so a brand new row gets at most a 30% boost. Keeping the adjustments multiplicative and bounded means a fresh but irrelevant row cannot outrank a strong match — a common failure of additive boosts.

Any column works here: click-through rate, purchase count, editorial priority, or a per-user affinity score joined from another table. Because these live in the same database as the index, there is no second round trip and no separate copy to keep in sync.

## Diversifying Results

A top 10 made of ten near-identical rows is usually worse than a more varied one, even when every row scores well. Cap how many results each group may contribute using a window function over the candidate set:

<CodeGroup>
```sql SQL
WITH lexical AS (...), semantic AS (...), fused AS (...)
SELECT id, description, category, score
FROM (
    SELECT m.id, m.description, m.category, f.score,
           ROW_NUMBER() OVER (PARTITION BY m.category ORDER BY f.score DESC, m.id) AS per_category
    FROM fused f
    JOIN mock_items m USING (id)
) t
WHERE per_category <= 2
ORDER BY score DESC, id
LIMIT 5;
```

</CodeGroup>

This runs over the already-narrowed candidate set, so the `PARTITION BY` is cheap. It is also the reason to over-fetch: capping groups discards rows, and the discarded ones must be replaced from deeper in the candidate list.

## Handing Off to a Relevance Model

A dedicated reranking model scores the query and each document **together**, rather than comparing two independently computed embeddings. This catches negation, word sense, and fine distinctions that a vector comparison flattens, at a cost of one model call per candidate. That cost is why it belongs at the end of the funnel, over tens of rows rather than millions.

These models run outside the database. ParadeDB's role is to hand over a small candidate set with everything the model needs, in one query:

<CodeGroup>
```sql SQL
WITH lexical AS (...), semantic AS (...), fused AS (...)
SELECT m.id, m.description, f.score AS rrf,
       l.rank AS lexical_rank,
       s.rank AS semantic_rank
FROM fused f
JOIN mock_items m USING (id)
LEFT JOIN lexical l USING (id)
LEFT JOIN semantic s USING (id)
ORDER BY f.score DESC, m.id
LIMIT 50;
```

</CodeGroup>

The `LEFT JOIN`s carry each branch's rank through even for rows only one branch found, so the model receives both signals along with the text. Add any other feature the model or your ranking logic uses — they are ordinary columns.

Your application then scores the 50 rows and reorders them. Keep this step cancellable and fall back to the fused order on timeout, since it will dominate your tail latency.

<Warning>
  Avoid calling an external model from inside the query with extensions like
  `pgsql-http` or an untrusted procedural language. The call runs inside the
  transaction holding a snapshot open, has no connection pooling, may be invoked
  more times than expected, and a timeout aborts the entire query. Retrieve the
  candidates, then rerank outside the database.
</Warning>

## Returning Fewer Results

Reranking is not filtering, but a model that returns calibrated relevance scores lets you add a filter afterward. Dropping everything below a cutoff returns fewer results — or none — instead of ten confident-looking irrelevant rows:

```sql
WHERE rerank_score > 0.3
```

Choose the cutoff from a labelled query set, including queries that should return nothing. Treat it as a separate decision from the ranking itself.

## Common Mistakes

- **Reranking a candidate set that is too small.** With only 10 candidates there is nothing to promote, so reranking just shuffles the same rows.
- **Using a reranker to fix a retrieval problem.** If the relevant rows never entered the candidate set, widen the branch `LIMIT` or fix the query first.
- **Unbounded boosts.** An additive recency or popularity term with no ceiling will eventually outrank relevance entirely. Prefer bounded multiplicative factors.
- **Tuning by intuition.** Weights, decay constants, and cutoffs interact. Change one at a time against a fixed set of labelled queries.
