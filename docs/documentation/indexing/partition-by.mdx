<Warning>

  under active development. Query pruning and join planning optimizations are
  actively evolving. Syntax and internal planner behaviors may change in future
  releases.
</Warning>

By default, a ParadeDB index does not partition rows across segments by column values.
Using the `partition_by` option in `CREATE INDEX`, you can partition the index space along one or more columns:

```sql
CREATE INDEX items_idx ON items
USING paradedb (id, tenant_id, description, created_at)
WITH (
  key_field = 'id',
  partition_by = 'tenant_id',
  target_segment_count = 16
);
```

Partitioning an index provides two key benefits:

1. Segment Pruning: Accelerate search and filter queries by skipping non-matching segments before scanning them.
2. Range Co-Partitioned Joins: Accelerate parallel joins by aligning segment boundaries on join keys. Workers can join matching slices locally without exchanging data across processes, allowing operations like Top-K sorting and aggregations to run worker-locally before gathering results.

---

## How It Works

When an index is built or reindexed with `partition_by`, ParadeDB divides rows across segments based on the values in the partitioned columns:

- Each segment records the min and max values (bounding range) of the partition columns in its metadata.
- When a query filters on a partition column, ParadeDB checks the filter against each segment's range and skips segments that cannot contain matching rows before opening them.
- If a segment's range falls entirely within a query filter (for example, the segment's `created_at` range is in 2024 and the query filters `created_at >= '2024-01-01'`), ParadeDB omits that filter evaluation when scanning that segment.

<Note>
  Partition boundaries are established during `CREATE INDEX` or `REINDEX` and
  are not yet rebalanced as new data is inserted. Query performance will
  gradually decline as writes accumulate. Running `REINDEX` restores optimal
  partition boundaries. Incremental maintenance across ongoing writes is planned
  for future releases.
</Note>

## Partitioning on Multiple Columns

You can partition an index along multiple columns by specifying a comma-separated list:

```sql
CREATE INDEX events_idx ON events
USING paradedb (id, organization_id, created_at, message)
WITH (
  key_field = 'id',
  partition_by = 'organization_id, created_at',
  target_segment_count = 32
);
```

### Comparison to Sorted Indexes

In a standard Postgres B-tree index over multiple columns (such as `(organization_id, created_at)`), rows are sorted lexicographically by the first column, then the second. Because of this:

- Queries must filter on the leading column (`organization_id`) to use the index efficiently.
- A filter on `created_at` alone cannot skip non-matching index pages.

In contrast, `partition_by` does not define a sorted prefix key. Instead, ParadeDB partitions rows multi-dimensionally across the specified columns:

- No column order dependency: Queries do not need to include the leading column or all columns to benefit from pruning. Filtering on `organization_id` alone, `created_at` alone, or both columns simultaneously allows ParadeDB to prune non-matching segments.
- Pruning trade-offs per column: Because `target_segment_count` controls the total number of segments, that segment budget is divided across all partition columns. For example, with `target_segment_count = 16`, partitioning on `organization_id` alone creates ~16 slices along organization ID. Partitioning on `organization_id, created_at` divides those 16 segments across both dimensions (e.g. roughly 4 slices per column).

As a result, the more columns you include in `partition_by`, the less effective pruning will be for each individual column. For most workloads, partitioning on 1 or 2 high-selectivity columns that frequently appear in queries or join conditions gives the best results.

## Column Selection Guidance

Choosing the right column(s) for `partition_by` depends on your query patterns and join requirements.

### Decision Matrix

| Workload / Primary Pattern                           | Recommended `partition_by` Column                                                | Expected Impact                                                                                                                               |
| :--------------------------------------------------- | :------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------- |
| Multi-Tenant SaaS (queries filter by tenant)         | Tenant ID (e.g. `tenant_id`, `org_id`)                                           | Pruning: Queries filter on `tenant_id = ?`, bypassing non-matching segments entirely to reduce I/O and cache churn.                           |
| Time-Series / Event Logs (queries filter by recency) | Timestamp / Date (e.g. `created_at`, `event_time`)                               | Pruning: Range filters (`created_at >= ...`) skip older or non-matching segments.                                                             |
| Large-Scale Joins (e.g. `orders` JOIN `items`)       | Equi-join key on both tables (e.g. `orders.item_id` and `items.id`)              | Co-Partitioned Joins: Joins and downstream operations (aggregates, Top-K) execute worker-locally without inter-worker data exchange.          |
| Multi-Tenant with Joins                              | Shared tenant key on both tables (e.g. `orders.tenant_id` and `items.tenant_id`) | Dual Benefit: Segment pruning for single-tenant searches and worker-local joins within a tenant.                                              |
| Multiple Query Filters                               | Multiple columns (e.g. `tenant_id, created_at`)                                  | Multi-Dimensional Pruning: Enables pruning on tenant equality, timestamp ranges, or both, with segment granularity divided among the columns. |

### Physical Over-Partitioning

By default, `CREATE INDEX` sets `target_segment_count` equal to the number of CPUs on the system. When using `partition_by`, we recommend physically over-partitioning by setting `target_segment_count` to 2–8X the CPU core count (or parallel worker count).

Over-partitioning provides two key advantages:

1. Better filter elimination: Smaller segments have narrower value ranges. A higher segment count allows queries to prune away a larger fraction of non-matching data.
2. Aligned joins across tables: Two tables being joined (e.g. `users` and `posts`) almost never share identical row counts or key distributions. Creating finer-grained physical segments gives the join planner the flexibility to align matching partition ranges across workers with minimal overlap.

#### Trade-Off: Segment Metadata Overhead

The ceiling on physical over-partitioning is segment metadata overhead. Each segment maintains its own dictionary, posting lists, and metadata structures. Creating hundreds or thousands of tiny segments increases file descriptor usage and memory pressure. Sizing `target_segment_count` to 2–8X CPU cores strikes a practical balance between pruning efficiency and segment overhead.

```sql
-- Example: On an 8-core machine, over-partition by 4X (target_segment_count = 32)
CREATE INDEX users_idx ON users USING paradedb (id, name)
WITH (key_field = 'id', partition_by = 'id', target_segment_count = 32);

CREATE INDEX posts_idx ON posts USING paradedb (id, owner_user_id, title)
WITH (key_field = 'id', partition_by = 'owner_user_id', target_segment_count = 32);
```

### Column Eligibility Rules

Columns specified in `partition_by` must meet the following constraints:

1. Single-valued only: Multi-valued types (such as arrays `TEXT[]`, `INT[]` and JSON/JSONB fields) cannot be used.
2. Columnar indexed: The column must be columnar indexed. Scalar types (integers, floats, booleans, dates, timestamps, UUIDs) are columnar indexed by default.
3. Raw ordering for text columns: If a text column is used in `partition_by`, it must use the [`literal`](/documentation/tokenizers/available-tokenizers/literal) tokenizer (e.g. `(tenant_code::pdb.literal)`).
4. Avoid low-cardinality standalone columns: Avoid using columns with very few distinct values (such as a boolean `is_active` flag) as the sole partition column, as a column with only 2 distinct values cannot produce more than 2 partitions.

## Segment Pruning

When queries include equality filters, `IN` lists, or range conditions on `partition_by` columns, ParadeDB compares those filters against the per-segment bounding ranges:

- Segments with non-overlapping ranges are excluded before opening index readers or posting lists.
- Segments whose ranges are completely contained within a filter can skip evaluating that filter clause.
- The planner sizes worker allocations based on surviving segments rather than total segments.

### Example: Multi-Tenant Pruning

```sql
CREATE TABLE documents (
  id BIGSERIAL PRIMARY KEY,
  tenant_id INT NOT NULL,
  title TEXT NOT NULL,
  body TEXT NOT NULL
);

CREATE INDEX documents_idx ON documents
USING paradedb (id, tenant_id, title, body)
WITH (
  key_field = 'id',
  partition_by = 'tenant_id',
  target_segment_count = 8
);
```

When querying a specific tenant:

```sql
EXPLAIN (COSTS OFF)
SELECT id, title
FROM documents
WHERE tenant_id = 42 AND body ||| 'database'
LIMIT 10;
```

ParadeDB scans only the segment containing `tenant_id = 42`, leaving the other 7 segments untouched.

## Range Co-Partitioned Joins

Without range co-partitioning, parallel joins must exchange rows between worker processes to match join keys:

- The build side may be broadcast to all workers, or
- Both sides are repartitioned by hash and shuffled across workers.

When both tables are partitioned on their equi-join keys using `partition_by`, ParadeDB coordinates matching partition ranges across the two scans. Parallel workers can then join their local slices directly without exchanging data between processes:

```sql
SET paradedb.enable_join_custom_scan TO on;
SET paradedb.enable_range_partitioned_join TO on;
```

### Execution Strategy

1. Worker-local joins: In parallel execution, each worker joins only its corresponding range partition of Table A with Table B directly over the index scans, eliminating cross-worker data shuffle.
2. Worker-local cardinality reduction: Operations like Top-K limit sorts or partial aggregations execute worker-locally before results are gathered to the leader process.
3. Partition elimination: Partitions with non-overlapping ranges between the two tables are skipped entirely without scanning.

<Note>
  The `Network*` nodes in execution plans (such as `NetworkShuffleExec` and
  `NetworkCoalesceExec`) represent shared-memory IPC communication between
  Postgres worker processes, rather than physical network socket calls.
</Note>

### Query Plan Comparison

Consider joining two tables `files` and `pages` on `files.id = pages.file_id`:

```sql
SELECT f.title, p.size_bytes
FROM files f JOIN pages p ON f.id = p.file_id
WHERE f.content @@@ 'Section'
ORDER BY f.title, p.size_bytes
LIMIT 10;
```

#### Without `partition_by` (Data Shuffled Across Workers)

Without co-partitioning, rows from each table must be repartitioned by hash and shuffled across worker processes (via shared-memory IPC) before the join can execute:

```txt
┌───── DistributedExec
│ SortPreservingMergeExec: [title ASC, size_bytes ASC], fetch=10
│   [Stage 3] => NetworkCoalesceExec
└──────────────────────────────────────────────────
  ┌───── Stage 3
  │ SortExec: TopK(fetch=10), expr=[title ASC, size_bytes ASC]
  │   HashJoinExec: mode=Partitioned, join_type=Inner, on=[(id, file_id)]
  │     [Stage 1] => NetworkShuffleExec
  │     [Stage 2] => NetworkShuffleExec
  └──────────────────────────────────────────────────
    ┌───── Stage 1
    │ RepartitionExec: partitioning=Hash([id])
    │   PgSearchScan: table=files
    └──────────────────────────────────────────────────
    ┌───── Stage 2
    │ RepartitionExec: partitioning=Hash([file_id])
    │   PgSearchScan: table=pages
    └──────────────────────────────────────────────────
```

#### With `partition_by` (Worker-Local Join)

When both indexes are partitioned on the join keys (`files.id` and `pages.file_id`) and `paradedb.enable_range_partitioned_join = on`, the join executes worker-locally in a single stage:

```txt
┌───── DistributedExec
│ SortPreservingMergeExec: [title ASC, size_bytes ASC], fetch=10
│   [Stage 1] => NetworkCoalesceExec
└──────────────────────────────────────────────────
  ┌───── Stage 1
  │ SortExec: TopK(fetch=10), expr=[title ASC, size_bytes ASC]
  │   HashJoinExec: mode=Partitioned, join_type=Inner, on=[(id, file_id)]
  │     PgSearchScan: table=files, partition=id[-∞..68)
  │     PgSearchScan: table=pages, partition=file_id[-∞..68)
  └──────────────────────────────────────────────────
```

Notice that:

- Scans, the join, and `SortExec: TopK` run together in a single stage (`Stage 1`).
- There is no intermediate worker-to-worker shuffle (`NetworkShuffleExec`).
- Results are coalesced only once at the end via `NetworkCoalesceExec` before returning to the leader.

## Configuration & GUCs

| Parameter                                | Type         | Default         | Description                                                                                                                        |
| :--------------------------------------- | :----------- | :-------------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| `partition_by`                           | Index Option | `""` (disabled) | Comma-separated list of columnar indexed fields used to partition segments.                                                        |
| `target_segment_count`                   | Index Option | CPU count       | Target number of segments to produce during build or reindex. When using `partition_by`, recommend setting to 2–8X CPU core count. |
| `paradedb.enable_range_partitioned_join` | GUC          | `off`           | Enables range co-partitioning optimizations for parallel joins.                                                                    |
| `paradedb.enable_join_custom_scan`       | GUC          | `on`            | Enables or disables ParadeDB custom join execution.                                                                                |
