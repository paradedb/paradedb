## BM25 Parameters

<Note>Tuning BM25 parameters is not necessary for most use cases.</Note>

BM25 scoring has two tunable parameters: `k1` controls how much repeated matches contribute to a score, and `b` controls how field length affects that score. Configure them per field when creating an index by passing quoted `key=value` options to the field's tokenizer type. These type modifiers are also called **typmods**.

| Parameter | Default | Accepted Range          | Effect                                                                                                                                                                                                                                                                            |
| --------- | ------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `k1`      | `1.2`   | `0` to `100`, inclusive | Controls term frequency saturation: how quickly additional occurrences of a query term stop adding much to the score. Lower values saturate sooner; higher values give repeated occurrences more weight. At `0`, term frequency and field length no longer affect a term's score. |
| `b`       | `0.75`  | `0` to `1`, inclusive   | Controls field length normalization relative to the average length of that field. Higher values penalize longer fields more strongly. At `0`, length normalization is disabled; at `1`, full length normalization is applied.                                                     |

For example, this index uses different scoring parameters for a short title and a longer body:

```sql
CREATE TABLE articles (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title TEXT,
  body TEXT
);

CREATE INDEX articles_idx ON articles
USING paradedb (
  id,
  (title::pdb.simple('k1=0.9', 'b=0.3')),
  (body::pdb.simple('k1=1.5', 'b=0.75'))
)
WITH (key_field='id');
```

You can set either parameter independently; an omitted parameter keeps its default. The options work with other [tokenizers](/reference/tokenizers/overview) and can be combined with [token filters](/reference/token-filters/overview), such as `pdb.simple('stemmer=english', 'k1=1.5', 'b=0.75')`.

Queries use the parameters stored in the index without repeating the typmods:

```sql
SELECT id, title, pdb.score(id)
FROM articles
WHERE title ||| 'search' OR body ||| 'search'
ORDER BY pdb.score(id) DESC, id
LIMIT 10;
```

### Choosing Values

Start with the defaults and evaluate changes against representative queries and relevance judgments. As an initial tuning range, try `k1` between `0.5` and `2.0` and `b` between `0.3` and `0.9`. These are starting points for experiments, not limits or guarantees of better relevance.

- **Short titles or labels:** Try a lower `k1` when repeating a word should add little relevance. A lower `b` can also prevent slightly longer titles from being penalized too much.
- **Long articles or descriptions:** Try a higher `k1` when repeated mentions are a useful relevance signal. Increase `b` when long documents rank highly mainly because they contain more words.
- **Fields whose length should not matter:** Set `b=0` when additional text should not reduce a match's score.
- **Term presence should matter, but repetition should not:** Set `k1=0`. For a single-term query on that field, all matching documents receive the same term score, based on inverse document frequency.

<Note>
  These parameters are part of the index definition. To change them on an
  existing index, drop and recreate the index with the new typmods. `REINDEX`
  rebuilds the existing definition and does not change the parameters.
</Note>

## Boosting

Boosting increases or decreases the impact of a specific query by multiplying its contribution to the overall [BM25 score](/reference/full-text/score).

To boost a query, cast the query to the `boost` type. In this example, the `shoes` query is weighted twice as heavily as the `footwear` query.

<CodeGroup>
```sql SQL
SELECT id, pdb.score(id), description, category
FROM mock_items
WHERE description ||| 'shoes'::pdb.boost(2) OR category ||| 'footwear'
ORDER BY score DESC
LIMIT 5;
```

```ts Drizzle
import { desc, or } from "drizzle-orm";
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({
    id: mockItems.id,
    score: search.score(mockItems.id),
    description: mockItems.description,
    category: mockItems.category,
  })
  .from(mockItems)
  .where(
    or(
      search.matchAny(mockItems.description, search.boost("shoes", 2)),
      search.matchAny(mockItems.category, "footwear"),
    ),
  )
  .orderBy(desc(search.score(mockItems.id)))
  .limit(5);
```

```python Django
from django.db.models import Q
from paradedb import Boost, MatchAny, ParadeDB, Score

MockItem.objects.filter(
    Q(description=ParadeDB(MatchAny(Boost('shoes', 2)))) |
    Q(category=ParadeDB(MatchAny('footwear')))
).annotate(
    score=Score()
).values('id', 'score', 'description', 'category').order_by('-score')[:5]
```

```python SQLAlchemy
from sqlalchemy import desc, or_, select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import pdb, search

stmt = (
    select(
        MockItem.id,
        pdb.score(MockItem.id).label("score"),
        MockItem.description,
        MockItem.category,
    )
    .where(
        or_(
            search.match_any(MockItem.description, search.boost("shoes", 2.0)),
            search.match_any(MockItem.category, "footwear"),
        )
    )
    .order_by(desc("score"))
    .limit(5)
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
MockItem.search(:description)
        .match_any(ParadeDB.boost("shoes", 2))
        .or(MockItem.search(:category).match_any("footwear"))
        .with_score
        .select(:id, :description, :category)
        .order(search_score: :desc)
        .limit(5)
```

```cs EF Core
await dbContext
    .MockItems.Where(item =>
        EF.Functions.MatchAny(item.Description, Pdb.Boost("shoes", 2))
        || EF.Functions.MatchAny(item.Category, "footwear")
    )
    .Select(item => new
    {
        item.Id,
        Score = EF.Functions.Score(item.Id),
        item.Description,
        item.Category
    })
    .OrderByDescending(item => item.Score)
    .Take(5)
    .ToListAsync();
```

</CodeGroup>

`boost` takes a numeric value, which is the multiplicative boost factor. It can be any floating point number between `-2048` and `2048`.

[Query builder functions](/reference/full-text/query-builder) can also be boosted:

<CodeGroup>
```sql SQL
SELECT id, description, category, pdb.score(id)
FROM mock_items
WHERE description @@@ pdb.regex('key.*')::pdb.boost(2)
ORDER BY score DESC
LIMIT 5;
```

## Constant Scoring

Constant scoring assigns the same score to all documents that match a query. To apply a constant score, cast the query to the `const` type with a
numeric value.

For instance, the following query assigns a score of `1` to all documents matching the query `shoes`.

<CodeGroup>
```sql SQL
SELECT id, pdb.score(id), description, category
FROM mock_items
WHERE description ||| 'shoes'::pdb.const(1)
ORDER BY score DESC
LIMIT 5;
```

```ts Drizzle
import { desc } from "drizzle-orm";
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({
    id: mockItems.id,
    score: search.score(mockItems.id),
    description: mockItems.description,
    category: mockItems.category,
  })
  .from(mockItems)
  .where(search.matchAny(mockItems.description, search.constant("shoes", 1)))
  .orderBy(desc(search.score(mockItems.id)))
  .limit(5);
```
