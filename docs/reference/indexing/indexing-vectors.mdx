<Note>
  This is a beta feature available in versions `0.25.0` and above. We strongly
  recommend `0.27.0` or later for substantial vector search improvements. See
  [How Vector Search Works](/concepts/vector/overview) for background.
</Note>

ParadeDB provides `pdb.vector(N)`, a dense vector type containing `N` single-precision
floats. It does not require pgvector. Existing pgvector `vector(N)` columns are
also supported, with the same index structures and search behavior.

For example:

```sql
CREATE TABLE items (id bigint PRIMARY KEY, embedding pdb.vector(3));
INSERT INTO items VALUES (1, '[1, 2, 3]');
CREATE INDEX items_search ON items
USING paradedb (id, embedding pdb.vector_cosine_ops);
```

You can cast `real[]` and `double precision[]` arrays to `pdb.vector(N)`. Arrays
must be one-dimensional, contain no NULL elements, and contain only finite
values after conversion to single precision. A vector must contain between 1
and 16,000 elements, and `pdb.vector(N)` enforces the declared length.

When pgvector is installed, casts between its `vector` type and `pdb.vector`
reuse the same binary representation without converting the elements:

```sql
SELECT '[1, 2, 3]'::vector::pdb.vector;
SELECT '[1, 2, 3]'::pdb.vector::vector;
```

Compatibility is registered automatically in either extension installation order,
including when pgvector is installed in a different schema.
Existing pgvector columns and their ParadeDB indexes do not need to be rebuilt.

## Creating the Index

The `mock_items` table comes with an `embedding` column of type `pdb.vector(8)` populated with sample embeddings.
In this example, `embedding` is added to the ParadeDB index with cosine similarity as the distance function.

<CodeGroup>
```sql SQL
CREATE INDEX search_idx ON mock_items
USING paradedb (id, description, category, embedding pdb.vector_cosine_ops);
```

```ts Drizzle
import { indexing } from "@paradedb/drizzle-paradedb";

// In the pgTable definition:
(table) => [
  indexing
    .paradedbIndex("search_idx")
    .on(
      table.id,
      table.description,
      table.category,
      indexing.vectorField(table.embedding, "cosine"),
    ),
];
```

```python Django
from django.db import connection
from paradedb.indexes import ParadeDBIndex

with connection.schema_editor() as schema_editor:
    schema_editor.add_index(
        MockItem,
        ParadeDBIndex(
            fields={
                "id": {},
                "description": {},
                "category": {},
                "embedding": {"metric": "cosine"},
            },
            name="search_idx",
        ),
    )
```

```python SQLAlchemy
from sqlalchemy import Index
from paradedb.sqlalchemy import indexing

idx = Index(
    "search_idx",
    indexing.ParadeDBField(MockItem.id),
    indexing.ParadeDBField(MockItem.description),
    indexing.ParadeDBField(MockItem.category),
    indexing.VectorField(MockItem.embedding, metric="cosine"),
    postgresql_using="paradedb",
)

with engine.begin() as conn:
    idx.create(conn)
```

```ruby Rails
ActiveRecord::Base.connection.add_paradedb_index(
  :mock_items,
  fields: {
    id: {},
    description: {},
    category: {},
    embedding: { metric: :cosine }
  },
  name: :search_idx
)
```

```cs EF Core
modelBuilder.Entity<MockItem>()
    .HasParadeDbIndex("search_idx", e => e.Id)
    .HasField(e => e.Description)
    .HasField(e => e.Category)
    .HasField(e => e.Embedding, VectorMetric.Cosine);
```

</CodeGroup>

The desired distance function is encoded into the index definition, and cannot be changed without reindexing.

<CodeGroup>
```sql SQL
embedding pdb.vector_l2_ops      -- L2 (default)
embedding pdb.vector_cosine_ops  -- cosine
embedding pdb.vector_ip_ops      -- inner product
```

```ts Drizzle
indexing.vectorField(mockItems.embedding, "l2"); // L2 (default)
indexing.vectorField(mockItems.embedding, "cosine"); // cosine
indexing.vectorField(mockItems.embedding, "ip"); // inner product
```

```python Django
"embedding": {"metric": "l2"}      # L2 (default)
"embedding": {"metric": "cosine"}  # cosine
"embedding": {"metric": "ip"}      # inner product
```

```python SQLAlchemy
indexing.VectorField(MockItem.embedding, metric="l2")      # L2 (default)
indexing.VectorField(MockItem.embedding, metric="cosine")  # cosine
indexing.VectorField(MockItem.embedding, metric="ip")      # inner product
```

```ruby Rails
embedding: { metric: :l2 }      # L2 (default)
embedding: { metric: :cosine }  # cosine
embedding: { metric: :ip }      # inner product
```

```cs EF Core
.HasField(e => e.Embedding, VectorMetric.L2)            // L2 (default)
.HasField(e => e.Embedding, VectorMetric.Cosine)        // cosine
.HasField(e => e.Embedding, VectorMetric.InnerProduct)  // inner product
```

</CodeGroup>

<Note>
  `pdb.vector` and pgvector's `vector` are supported. The `halfvec`,
  `sparsevec`, and `bit` types are not yet indexable. Each ParadeDB index
  currently supports one vector field, whose dimensions must be declared with
  `pdb.vector(N)` or pgvector's `vector(N)`. For pgvector columns, the existing
  unqualified `vector_l2_ops`, `vector_cosine_ops`, and `vector_ip_ops` classes
  remain supported.
</Note>

<Note>
  If you track index build progress with
  [`pg_stat_progress_create_index`](https://www.postgresql.org/docs/current/progress-reporting.html#CREATE-INDEX-PROGRESS-REPORTING),
  the `phase` column identifies partition sampling, vector partition training,
  and vector clustering. Row counters pause during training and clustering,
  which can be computationally expensive. These phases do not currently report a
  completion percentage. A leader that has finished its own work reports that it
  is waiting for workers to finish indexing/clustering.
</Note>

## Index Options

We recommend keeping the defaults, which work well for most workloads. The following options are available for development and debugging.

<CodeGroup>
```sql SQL
CREATE INDEX search_idx ON mock_items
USING paradedb (id, description, category, embedding pdb.vector_cosine_ops)
WITH (target_leaf_size=400, replication=2);
```

```ts Drizzle
import { indexing } from "@paradedb/drizzle-paradedb";

indexing
  .paradedbIndex("search_idx", {
    targetLeafSize: 400,
  })
  .on(
    mockItems.id,
    mockItems.description,
    mockItems.category,
    indexing.vectorField(mockItems.embedding, "cosine"),
  );
```

```python Django
from django.db import connection
from paradedb.indexes import ParadeDBIndex

with connection.schema_editor() as schema_editor:
    schema_editor.add_index(
        MockItem,
        ParadeDBIndex(
            fields={'id': {}, 'description': {}, 'category': {}, 'embedding': {'metric': 'cosine'}},
            name="search_idx",
            target_leaf_size=400,
        ),
    )
```

```python SQLAlchemy
from sqlalchemy import Index
from paradedb.sqlalchemy import indexing

idx = Index(
    "search_idx",
    indexing.ParadeDBField(MockItem.id),
    indexing.ParadeDBField(MockItem.description),
    indexing.ParadeDBField(MockItem.category),
    indexing.VectorField(MockItem.embedding, metric="cosine"),
    postgresql_using="paradedb",
    postgresql_with={'target_leaf_size': 400},
)

with engine.begin() as conn:
    idx.create(conn)
```

```ruby Rails
ActiveRecord::Base.connection.add_paradedb_index(
  :mock_items,
  fields: {
    id: {},
    description: {},
    category: {},
    embedding: { metric: :cosine },
  },
  name: :search_idx,
  index_options: { target_leaf_size: 400 }
)
```

```cs EF Core
modelBuilder.Entity<MockItem>()
    .HasParadeDbIndex("search_idx", e => e.Id)
    .HasField(e => e.Description)
    .HasField(e => e.Category)
    .HasField(e => e.Embedding, VectorMetric.Cosine)
    .HasTargetLeafSize(400);
```

</CodeGroup>

<ParamField body="training_sample_ratio" default={0.32}>
  Fraction of indexed vectors sampled for training whenever a segment is
  clustered. `0` chooses the fraction automatically based on available memory.
</ParamField>
<ParamField body="target_leaf_size" default={400}>
  The target number of indexed vectors in a cluster.
</ParamField>
<ParamField body="vector_router_quantization" default={true}>
  By default, cluster centroids are quantized. This makes them more compact and
  faster to search.
</ParamField>
<ParamField body="replication" default={2}>
  ParadeDB uses boundary replication, which means that vectors sitting close to
  two clusters are replicated across both. Replication improves recall. A higher
  value replicates to more clusters, at the cost of longer index build times and
  more storage.
</ParamField>
<ParamField body="quantization" default="[1,1]">
  ParadeDB uses two quantization layers by default, each receiving 1 bit per
  dimension. Each layer can use up to 4 bits. Set `quantization = 0` to disable
  quantization entirely. In our testing, the default `'[1,1]'` delivers the best
  performance.
</ParamField>
