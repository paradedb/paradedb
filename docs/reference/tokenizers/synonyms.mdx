With synonyms, a search for `sofa` also finds rows that say `couch`. You keep the rules in a regular Postgres table, and
a query reads them with a subquery. Changes to the rules are transactional and apply to the next query, without a
reindex.

## Creating a Synonym Index

Store one rule per row in a `pdb.synonym_rule` column, and create a ParadeDB index on that column alone:

```sql
CREATE TABLE shop_synonyms (rule pdb.synonym_rule NOT NULL);
INSERT INTO shop_synonyms VALUES
    ('couch, sofa, divan'),
    ('sneakers => running shoes');
CREATE INDEX shop_synonyms_idx ON shop_synonyms USING paradedb (rule);
```

Rules use the Solr format, which Elasticsearch and OpenSearch synonym files also use. There are two kinds:

- `couch, sofa, divan` is an equivalence rule. A search for any of these words finds all of them.
- `sneakers => running shoes` is a directed rule. A search for `sneakers` looks for `running shoes` instead, and a
  search for `running shoes` doesn't change.

If a word is in several rules, a search for it uses the alternatives of all of them. Rules don't chain. With
`sneakers, shoes, trainers` and `shoes, kicks`, a search for `shoes` finds all four words, but a search for `kicks`
finds only `kicks` and `shoes`.

Either side of a rule can have several words. A multi-word term matches as a phrase, so the field you search needs token
positions. All tokenizers keep them except [ngrams](/reference/tokenizers/available-tokenizers/ngrams), which needs
equal gram sizes and `positions=true`. An [edge ngrams](/reference/tokenizers/available-tokenizers/edge-ngrams) field
puts all the grams of a word at one position, so search it with a
[search tokenizer](/reference/tokenizers/search-tokenizer) that keeps words whole.

Escape a comma in a term with a backslash. Comments and blank lines are allowed. `INSERT` rejects a rule that doesn't
parse, and the error shows the rule and the reason.

To load a synonym file, use a delimiter and a quote character that never appear in it. Each line then becomes one rule,
backslashes included:

```sql
\copy shop_synonyms FROM 'synonyms.txt' WITH (FORMAT csv, DELIMITER E'\x01', QUOTE E'\x02')
```

### Tokenizers

A synonym index tokenizes its rules, and a query uses it only if the field you search has the same tokenizer. Set the
tokenizer with a cast, as for a text field. With a stemmer, a search for `couches` uses the rule for `couch`:

```sql
CREATE INDEX shop_synonyms_en_idx ON shop_synonyms
USING paradedb ((rule::pdb.simple('stemmer=english')));
```

Options at their default values don't count, so `pdb.simple` and `pdb.simple('lowercase=true')` are one tokenizer. If
you search fields with different tokenizers, create one synonym index for each tokenizer on the same table.

### Several Sets in One Table

To keep several sets of rules in one table, create a partial index for each set:

```sql
CREATE TABLE synonyms (set_name text NOT NULL, rule pdb.synonym_rule NOT NULL);
CREATE INDEX shop_idx ON synonyms USING paradedb (rule) WHERE set_name = 'shop';
CREATE INDEX colors_idx ON synonyms USING paradedb (rule) WHERE set_name = 'colors';
```

A query picks a set with the same `WHERE` clause, as shown below.

## Searching with Synonyms

The index you search needs no synonym setting:

```sql
CREATE INDEX search_idx ON mock_items
USING paradedb (id, description, category);
```

To expand a [match](/reference/full-text/match) query, give it a subquery on the rules table. `pdb.expand` takes the
search text and the rule column:

<CodeGroup>
```sql SQL
SELECT description FROM mock_items
WHERE description ||| (SELECT pdb.expand('sofa', rule) FROM shop_synonyms);
```

```ts Drizzle
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({ description: mockItems.description })
  .from(mockItems)
  .where(
    search.matchAny(
      mockItems.description,
      search.expand("sofa", shopSynonyms.rule),
    ),
  );
```

```python Django
from paradedb import Expand, MatchAny, ParadeDB

results = MockItem.objects.filter(
    description=ParadeDB(MatchAny(Expand('sofa', ShopSynonym, 'rule')))
).values('description')
list(results)
```

```python SQLAlchemy
from sqlalchemy import select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import search

rules = search.expand("sofa", ShopSynonym.rule)

stmt = (
    select(MockItem.description)
    .where(search.match_any(MockItem.description, rules))
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
MockItem.search(:description)
        .match_any(ParadeDB.expand("sofa", ShopSynonym, :rule))
        .select(:description)
        .to_a
```

```cs EF Core
await dbContext
    .MockItems.Where(item =>
        EF.Functions.MatchAny(
            item.Description,
            Pdb.Expand("sofa", dbContext.ShopSynonyms.Select(s => s.Rule))
        )
    )
    .Select(item => new { item.Description })
    .ToListAsync();
```

</CodeGroup>

Without the subquery, or if it returns no rules, the query searches only the typed words.

Each run of query words that matches a rule becomes a group, and a row matches the group if it contains any of its
alternatives. With `&&&`, every group has to match. When rules overlap, the longest run wins. Because a multi-word term
matches as a phrase, a `|||` search for `running shoes` with the rule `running shoes, joggers` doesn't find a row that
has only `shoes`.

`pdb.expand` works with `|||`, `&&&`, [`###`](#phrases) and [`@@@`](#query-parser). It is an error with a
[term](/reference/full-text/term) query. It takes text and not a text array such as `ARRAY['sofa']`, which has no
tokenizer to match the rules with.

Put the fuzzy and boost casts on the subquery:

<CodeGroup>
```sql SQL
SELECT description FROM mock_items
WHERE description ||| (SELECT pdb.expand('sofa', rule) FROM shop_synonyms)::pdb.fuzzy(1);
```

```ts Drizzle
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({ description: mockItems.description })
  .from(mockItems)
  .where(
    search.matchAny(
      mockItems.description,
      search.fuzzy(search.expand("sofa", shopSynonyms.rule), 1),
    ),
  );
```

```python Django
from paradedb import Expand, Fuzzy, MatchAny, ParadeDB

results = MockItem.objects.filter(
    description=ParadeDB(MatchAny(Fuzzy(Expand('sofa', ShopSynonym, 'rule'), 1)))
).values('description')
list(results)
```

```python SQLAlchemy
from sqlalchemy import select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import search

rules = search.expand("sofa", ShopSynonym.rule)

stmt = (
    select(MockItem.description)
    .where(search.match_any(MockItem.description, search.fuzzy(rules, 1)))
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
MockItem.search(:description)
        .match_any(ParadeDB.fuzzy(ParadeDB.expand("sofa", ShopSynonym, :rule), 1))
        .select(:description)
        .to_a
```

```cs EF Core
await dbContext
    .MockItems.Where(item =>
        EF.Functions.MatchAny(
            item.Description,
            Pdb.Fuzzy(Pdb.Expand("sofa", dbContext.ShopSynonyms.Select(s => s.Rule)), 1)
        )
    )
    .Select(item => new { item.Description })
    .ToListAsync();
```

</CodeGroup>

[Fuzzy](/reference/full-text/fuzzy) and prefix matching apply only to the typed words, and their alternatives match
exactly. A directed rule drops the typed words, fuzzy or not.

To use one set of a [table with several sets](#several-sets-in-one-table), add the `WHERE` of its partial index to the
subquery:

<CodeGroup>
```sql SQL
SELECT description FROM mock_items
WHERE description ||| (SELECT pdb.expand('sofa', rule) FROM synonyms WHERE set_name = 'shop');
```

```ts Drizzle
import { eq } from "drizzle-orm";
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({ description: mockItems.description })
  .from(mockItems)
  .where(
    search.matchAny(
      mockItems.description,
      search.expand("sofa", synonyms.rule, {
        where: eq(synonyms.setName, "shop"),
      }),
    ),
  );
```

```python Django
from paradedb import Expand, MatchAny, ParadeDB

rules = Expand('sofa', Synonym.objects.filter(set_name='shop'), 'rule')

results = MockItem.objects.filter(
    description=ParadeDB(MatchAny(rules))
).values('description')
list(results)
```

```python SQLAlchemy
from sqlalchemy import select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import search

rules = search.expand("sofa", Synonym.rule, where=Synonym.set_name == "shop")

stmt = (
    select(MockItem.description)
    .where(search.match_any(MockItem.description, rules))
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
rules = ParadeDB.expand("sofa", Synonym.where(set_name: "shop"), :rule)

MockItem.search(:description)
        .match_any(rules)
        .select(:description)
        .to_a
```

```cs EF Core
await dbContext
    .MockItems.Where(item =>
        EF.Functions.MatchAny(
            item.Description,
            Pdb.Expand(
                "sofa",
                dbContext.Synonyms.Where(s => s.SetName == "shop").Select(s => s.Rule)
            )
        )
    )
    .Select(item => new { item.Description })
    .ToListAsync();
```

</CodeGroup>

### Phrases

A [phrase](/reference/full-text/phrase) query takes the same subquery and searches one phrase for each combination of
alternatives. With the rule `sneakers => running shoes`, a search for `sleek sneakers` looks for `sleek running shoes`:

<CodeGroup>
```sql SQL
SELECT description FROM mock_items
WHERE description ### (SELECT pdb.expand('sleek sneakers', rule) FROM shop_synonyms);
```

```ts Drizzle
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({ description: mockItems.description })
  .from(mockItems)
  .where(
    search.phrase(
      mockItems.description,
      search.expand("sleek sneakers", shopSynonyms.rule),
    ),
  );
```

```python Django
from paradedb import Expand, ParadeDB, Phrase

results = MockItem.objects.filter(
    description=ParadeDB(Phrase(Expand('sleek sneakers', ShopSynonym, 'rule')))
).values('description')
list(results)
```

```python SQLAlchemy
from sqlalchemy import select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import search

rules = search.expand("sleek sneakers", ShopSynonym.rule)

stmt = (
    select(MockItem.description)
    .where(search.phrase(MockItem.description, rules))
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
MockItem.search(:description)
        .phrase(ParadeDB.expand("sleek sneakers", ShopSynonym, :rule))
        .select(:description)
        .to_a
```

```cs EF Core

    .MockItems.Where(item =>
        EF.Functions.Phrase(
            item.Description,
            Pdb.Expand("sleek sneakers", dbContext.ShopSynonyms.Select(s => s.Rule))
        )
    )
    .Select(item => new { item.Description })
    .ToListAsync();
```

</CodeGroup>

The [slop](/reference/full-text/phrase#adding-slop) cast goes on the subquery and applies to every phrase. Each word
with a rule multiplies the phrases, up to [`paradedb.synonyms_max_alternatives`](#limits).

### Query Parser

The [query parser](/reference/full-text/query-parser) takes the same subquery when the left side is a text or JSON
field. It expands each word on its own and each quoted phrase as a [phrase](#phrases). An operator such as `AND` or `-`
applies to a word and its alternatives:

<CodeGroup>
```sql SQL
SELECT description FROM mock_items
WHERE description @@@ (SELECT pdb.expand('sleek AND sneakers', rule) FROM shop_synonyms);
```

```ts Drizzle
import { search } from "@paradedb/drizzle-paradedb";

await db
  .select({ description: mockItems.description })
  .from(mockItems)
  .where(
    search.parse(
      mockItems.description,
      search.expand("sleek AND sneakers", shopSynonyms.rule),
    ),
  );
```

```python Django
from paradedb import Expand, ParadeDB, Parse

results = MockItem.objects.filter(
    description=ParadeDB(Parse(Expand('sleek AND sneakers', ShopSynonym, 'rule')))
).values('description')
list(results)
```

```python SQLAlchemy
from sqlalchemy import select
from sqlalchemy.orm import Session
from paradedb.sqlalchemy import search

rules = search.expand("sleek AND sneakers", ShopSynonym.rule)

stmt = (
    select(MockItem.description)
    .where(search.parse(MockItem.description, rules))
)

with Session(engine) as session:
    session.execute(stmt).all()
```

```ruby Rails
MockItem.search(:description)
        .parse(ParadeDB.expand("sleek AND sneakers", ShopSynonym, :rule))
        .select(:description)
        .to_a
```

```cs EF Core
await dbContext
    .MockItems.Where(item =>
        EF.Functions.Parse(
            item.Description,
            Pdb.Expand("sleek AND sneakers", dbContext.ShopSynonyms.Select(s => s.Rule))
        )
    )
    .Select(item => new { item.Description })
    .ToListAsync();
```

</CodeGroup>

Because the parser expands each word on its own, a multi-word term expands only inside quotes. Only the field on the
left side expands, at every path of a JSON field. Words for other fields, such as `category:sofa`, stay as typed, and so
do ranges, sets and prefix phrases.

Phrase slop goes in the query string, as in `"red sofa"~2`, and not on the subquery. The `lenient` and
`conjunction_mode` options of `pdb.parse` are not available. The parser doesn't use a
[search tokenizer](/reference/tokenizers/search-tokenizer), so the query uses the synonym index with the tokenizer of
the field.

### Which Index a Query Uses

The subquery reads a table, not an index. The query uses the synonym index on the rule column that holds the rows the
subquery reads. That is the index on the whole table for a subquery without `WHERE`, or the partial index with the same
`WHERE`. The index also needs the tokenizer of the field you search. `EXPLAIN` shows it on a `Synonyms` line.

If no synonym index fits, or row-level security on the rules table applies to you, the query still expands. It reads the
rules on every run and tokenizes them with the tokenizer of the field. This is fine for a small set, and a warning says
why no index is used. Set `paradedb.planner_warnings` to `error` to catch it in your tests, or to `off` to hide it.

Postgres checks your privileges on the rules table, and row-level security applies, so each role expands with the rules
it can see.

In a prepared statement, the search text can be a parameter, but write the `WHERE` values of a partial index as
literals. After a few runs, Postgres can switch to a generic plan, and that plan can't tell which partial index holds
the rules. The ORM `expand` helpers write literals for you, except in EF Core, where you use a constant or
`EF.Constant`.

## Scoring

A group of single words scores as one term, so a rare synonym doesn't score above a common one. A row with both `sofa`
and `couch` scores a little above a row with only one of them. A group with a multi-word alternative or a fuzzy word
scores with its best alternative, and a phrase query scores a row with its best phrase.

To see which words of a group a row contains, [explain its score](/reference/full-text/score#score-explanation).

## Limits

Each alternative is one more term to look up. Two settings cap the work:

- `paradedb.synonyms_max_alternatives` (default `32`) caps the alternatives of one run of words, in sorted order, and
  the phrases of a phrase query. If a rule lists the typed words, the cap keeps them.
- `paradedb.synonyms_max_rules_per_key` (default `1024`) caps the rules that one word reads in each segment of the
  synonym index, or from the subquery if there is no index.

## Checking an Expansion

`EXPLAIN` shows the query before expansion. To see what a synonym index turns a text into, call `pdb.synonym_expansion`:

```sql
SELECT * FROM pdb.synonym_expansion('shop_synonyms_idx', 'red sofa');
```

```csv
 position | token |    alternatives
----------+-------+--------------------
        0 | red   | {red}
        1 | sofa  | {couch,divan,sofa}
(2 rows)
```
