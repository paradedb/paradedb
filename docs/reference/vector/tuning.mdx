title: Tuning Recall and Latency
description: Trade recall against latency for vector search
canonical: https://www.paradedb.com/docs/reference/vector/tuning
---

Vector search is approximate: it probes a subset of the index's vector clusters rather than scanning every vector. Probing more clusters improves recall (i.e. how often the true nearest neighbors are returned) at the cost of higher latency. One session-level setting controls this tradeoff:

```sql
SET paradedb.vector_cluster_max_probe = 0.02;
```

<ParamField body="paradedb.vector_cluster_max_probe" default={0.02}>
  Controls each segment's probe-work budget. Unfiltered queries scale the
  segment's capacity directly; filtered queries normalize that fraction using
  the filter's match rate so similar recall levels need more similar settings.
  Must be between `0.000001` and `1.0`, where `1.0` allows an exhaustive scan.
  Recall still depends on the query and filter, so measure it on your workload.
</ParamField>

Filtered queries use `budget = max_probe * cluster_count * c^exponent`, where
`c = open_share + (1 - open_share) * match_fraction` and
`exponent = clamp(-0.86 - 0.73 * ln(max_probe), 0, 2)`. The same resolved budget
controls routing, scan termination, and automatic router bypass. Cluster-open
and row charges are unchanged. Existing filtered-query probe settings should
be retuned for this scale.

For calibration, `paradedb.vector_probe_selectivity_exponent` sets the intercept
(default `-0.86`, range `[-2, 2]`) and
`paradedb.vector_probe_selectivity_slope` sets the log-probe slope
(default `-0.73`, range `[-1, 0]`). Set both to zero to use the original probe scale.

<Note>
  Recall also depends on the index's `training_sample_ratio` and
  `max_leaf_size`, applied whenever a segment is clustered. See [Index
  Options](/reference/indexing/indexing-vectors#index-options).
</Note>

## Inspecting Vector Indexes

Use `vector_info` to inspect vector storage and `vector_config` to check build settings. These examples inspect the `embedding` field of `search_idx`:

<CodeGroup>
```sql SQL
SELECT * FROM paradedb.vector_info('search_idx'::regclass, 'embedding');
SELECT * FROM paradedb.vector_config('search_idx'::regclass, 'embedding');
```

```ts Drizzle
import { diagnostics } from "@paradedb/drizzle-paradedb";

await db.execute(diagnostics.vectorInfo("search_idx", "embedding"));
await db.execute(diagnostics.vectorConfig("search_idx", "embedding"));
```

```python Django
from paradedb import paradedb_vector_info, paradedb_vector_config

paradedb_vector_info('search_idx', 'embedding')
paradedb_vector_config('search_idx', 'embedding')
```

```python SQLAlchemy
from paradedb.sqlalchemy import diagnostics

diagnostics.paradedb_vector_info(engine, "search_idx", "embedding")
diagnostics.paradedb_vector_config(engine, "search_idx", "embedding")
```

```ruby Rails
ParadeDB::Diagnostics.vector_info("search_idx", "embedding")
ParadeDB::Diagnostics.vector_config("search_idx", "embedding")
```

```cs EF Core
await dbContext.Database.VectorInfo("search_idx", "embedding").ToListAsync();
await dbContext.Database.VectorConfig("search_idx", "embedding").ToListAsync();
```

</CodeGroup>
