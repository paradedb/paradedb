title: ParadeDB vs. Alternatives
description: Compare ParadeDB with Postgres full-text search, pgvector, search engines, and vector stores

If you need search in your application, you can use vanilla Postgres search with `tsvector` and `pgvector`, add an external system like Elasticsearch or Pinecone, or use ParadeDB. The table below compares these options.

|                             | **Postgres FTS / pgvector**                                         | **External search systems (e.g., Elasticsearch)**                                | **ParadeDB**                                                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primary role**            | System of record with basic search and vector capabilities          | Search and retrieval engine                                         | System of record **and** search engine                                                                                                                               |
| **Search features**         | Basic FTS, vector search, and ranking primitives                    | Rich search and vector features, depending on the system             | BM25, fuzzy matching, faceting, vector search, and hybrid search                                                                                                     |
| **Analytics features**      | Standard Postgres aggregates over row-based storage                                  | Fast aggregates over columnar storage, depending on the system                       | Fast aggregates over columnar storage |
| **Replication lag**         | None in a single cluster                                            | Network latency and ETL transformation             | None in a single cluster                                                                                                                                             |
| **Operational complexity**  | Single database cluster      | Additional datastore, sync pipeline, and failure modes              | Single database cluster                                                                                              |
| **Scalability**             | Vertical scaling; horizontal scaling with read replicas or sharding | Horizontal scaling by distributing index shards across nodes, depending on the system            | Vertical scaling; horizontal scaling with read replicas or sharding                    |
| **Language**                | SQL                                                                 | Custom DSL or SDK                                                   | Standard SQL with custom search operators                                                                                                                            |
| **ACID guarantees**         | Full ACID compliance and read-after-write guarantees                | No multi-document ACID transactions                                 | Full ACID compliance and read-after-write guarantees                                                                                                                 |
| **Update & delete support** | Built for fast-changing data                                        | Operationally expensive for frequent updates and deletes | Built for fast-changing data                                                  |
